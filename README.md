
# Business Club Startups

Рабочий прототип модуля стартапов и вакансий для приложения Бизнес-клуба НИУ ВШЭ.

Сервис позволяет участникам Бизнес-клуба находить команду для стартапа, публиковать вакансии в свои проекты, откликаться на интересные предложения и анализировать компетенции формируемой команды.

## Локальный запуск

Для запуска требуются Docker и Docker Compose.

Из корневой директории проекта:

```bash
docker compose up --build
```

После запуска приложение доступно по адресам:

- Frontend: http://localhost:5173
- API: http://localhost:8000
- Swagger: http://localhost:8000/docs
- Health check: http://localhost:8000/health

При запуске backend автоматически применяет миграции Alembic.

### Создание локальных демонстрационных данных

После запуска Docker Compose выполните:

```bash
docker compose exec backend python -m app.db.seed
```

Seed-скрипт создаёт демонстрационных пользователей, публикации и отклик. Повторный запуск не создаёт повторно основные демонстрационные записи, которые уже существуют.

**Важно:** seed предназначен для локальной среды. Не запускайте его против заполненной production-базы Railway.

## Основной пользовательский сценарий

1. Пользователь авторизуется в приложении.
2. Создаёт стартап или вакансию.
3. Другой участник находит публикацию в ленте.
4. Открывает подробности предложения.
5. Отправляет отклик с сообщением.
6. Автор видит отклик в личном кабинете.
7. Автор принимает или отклоняет отклик.
8. Откликнувшийся участник видит результат в своём кабинете.

Один пользователь может одновременно быть автором собственных публикаций и кандидатом в других проектах.

Дополнительные механизмы расширяют основной сценарий:

- Smart Matching помогает студенту найти подходящий проект.
- Reverse Matching помогает автору оценить совпадения навыков кандидата.
- Team Readiness помогает определить, какие компетенции нужны команде после принятия участников.

Пользователь может:

- просматривать имя и email;
- изменять имя;
- добавлять информацию о себе;

Навыки используются рекомендательными механизмами приложения.

### Мои публикации

Пользователь может:

- просматривать собственные стартапы и вакансии;

- просматривать анализ компетенций формируемой команды.

При удалении публикации её отклики удаляются вместе с ней.

Возможные статусы:

- На рассмотрении;
- Принят;
- Отклонён.

Автор публикации может:

- видеть поступившие отклики;

- просматривать совпадения навыков кандидата и требований проекта;
- принимать или отклонять отклики.

Рекомендательная система не принимает решения автоматически.

## Публикации

Поддерживаются два типа:

```text
startup
vacancy
```

### Жизненный цикл публикации

```text
active -> closed -> active
```

Активные публикации отображаются в общей ленте.

Закрытые публикации:

- не отображаются в общей ленте;
- остаются доступны автору в личном кабинете;
- не принимают новые отклики;
- могут быть повторно открыты.

Автор также может полностью удалить собственную публикацию.

---

## Отклики

### Жизненный цикл отклика

```text
pending -> accepted
        -> rejected
```

После принятия или отклонения отклика повторное изменение решения запрещено.

Один пользователь не может отправить несколько откликов на одну публикацию.

Пользователь не может откликнуться на собственную публикацию.

## Ограничения доступа и безопасность

В приложении реализовано разграничение доступа.

### Публикации

- создать публикацию может только авторизованный пользователь;
- редактировать публикацию может только её автор;
- изменять статус публикации может только её автор;
- удалять публикацию может только её автор;
- вместе с удалённой публикацией удаляются связанные отклики.

### Отклики

- откликнуться может только авторизованный пользователь;
- нельзя откликнуться на собственную публикацию;
- нельзя повторно откликнуться на одну публикацию;
- нельзя откликнуться на закрытую публикацию;
- обрабатывать отклик может только автор соответствующей публикации;
- повторная обработка уже принятого или отклонённого отклика запрещена.

### Рекомендательные механизмы

- Smart Matching использует профиль текущего пользователя;
- Reverse Matching доступен автору публикаций при просмотре входящих откликов;
- Team Readiness доступен только автору соответствующей публикации;
- приватные поля пользователей не передаются в ответах рекомендательных API.

### Authentication

Для защищённых API используется JWT Bearer authentication.

Пароли не сохраняются в открытом виде. В базе хранится только хеш пароля.

Пользователь может изменить собственный пароль, указав текущий пароль. Изменить пароль другого пользователя через этот механизм нельзя.

Демонстрационные аккаунты имеют общий пароль исключительно для удобства проверки учебного приложения.

## API

### Authentication

```text
POST /auth/register
POST /auth/login
POST /auth/change-password
```

`POST /auth/change-password` требует авторизации и проверки текущего пароля. При успешной смене возвращается HTTP 204.

### Users

```text
GET   /users/me
PATCH /users/me
GET   /users/me/publications
```

### Publications

```text
GET    /publications
GET    /publications/recommended
GET    /publications/{id}
GET    /publications/{id}/team-readiness
POST   /publications
PATCH  /publications/{id}
DELETE /publications/{id}
```

Ответы API публикаций содержат `author_id` и `author_name`.

Имя автора загружается из базы пользователей и отражает изменения профиля. Email, хеш пароля, биография и навыки автора не включаются в публичные ответы публикаций.

`DELETE /publications/{id}` доступен только автору для активных и закрытых публикаций.

Ответы:

- 204 — успешное удаление;
- 401 — отсутствует авторизация;
- 403 — пользователь не является автором;
- 404 — публикация не найдена.

Удаление публикации и связанных откликов выполняется одной транзакцией. Другие публикации и пользователи сохраняются.

В интерфейсе удаление требует подтверждения; отмена не отправляет запрос на удаление.

### Applications

```text
POST  /publications/{id}/applications

GET   /applications/sent
GET   /applications/received

PATCH /applications/{id}/accept
PATCH /applications/{id}/reject
```

Интерактивная документация production API:

https://business-club-ai-native-production.up.railway.app/docs

## Двусторонний подбор команды

В приложении реализованы три взаимосвязанных механизма:

- **Smart Matching:** студент → подходящие проекты.
- **Reverse Matching:** автор проекта → совпадение навыков кандидатов.
- **Team Readiness:** принятые участники → покрытые и недостающие компетенции команды.

Все три механизма используют общий алгоритм сопоставления навыков.

### Smart Matching — персональные рекомендации

Авторизованный endpoint:

```text
GET /publications/recommended
```

Возвращает до трёх подходящих активных публикаций других пользователей.

Навыки из `User.skills` сопоставляются с требованиями `Publication.looking_for` по явному словарю синонимов.

Поддерживаются русский и английский языки, нормализация регистра и пунктуации.

Примеры:

- backend ↔ бэкенд;
- UX/UI ↔ дизайн интерфейсов;
- Python ↔ пайтон;
- product analytics ↔ продуктовая аналитика.

Сравниваются целые слова и последовательности слов. Поэтому `Java` не совпадает с `JavaScript`, а `SQL` — с `NoSQL`.

Ранжирование:

1. Чем больше различных совпавших навыков, тем выше публикация.
2. При равенстве совпадений выше располагается более новая публикация.
3. Повторные упоминания одного навыка не увеличивают его вес.

Ответ содержит публичные поля публикации, `matched_skills` и `explanation`.

Процент соответствия не вычисляется.

Собственные и закрытые публикации исключаются.

При пустых навыках или отсутствии совпадений возвращается пустой список.

#### Интерфейс

Над обычной лентой расположен блок «Рекомендуем вам».

Он показывает:

- подходящие стартапы и вакансии;
- совпадающие навыки;
- краткое объяснение рекомендации;
- ссылку на публикацию.

Если пользователь не указал навыки, интерфейс предлагает заполнить профиль.

Ошибка загрузки рекомендаций не блокирует обычную ленту.

### Reverse Matching — рекомендации автору

В разделе «Кабинет → Входящие» автор видит:

- имя кандидата;
- его сообщение;
- статус отклика;
- совпавшие навыки;
- объяснение соответствия требованиям.

Endpoint:

```text
GET /applications/received
```

Добавляет к входящим откликам:

```text
applicant_name
matched_skills
explanation
```

Данные возвращаются только для откликов на публикации текущего пользователя.

Нового публичного списка кандидатов нет. Email, биография, полный список навыков, пароли и хеши кандидатов не добавляются в ответ.

Smart Matching и Reverse Matching используют общие функции из:

```text
backend/app/services/matching.py
```

Например, навыки кандидата:

```text
Python, FastAPI, Backend
```

и требования:

```text
Python, бэкенд
```

дают совпадения:

```text
Backend, Python
```

При отсутствии навыков отображается нейтральное сообщение.

Отсутствие совпадений не считается доказательством того, что кандидат не подходит.

Решение о принятии или отклонении отклика всегда остаётся за автором проекта.

Результаты пересчитываются по текущим навыкам и требованиям. Исторические снимки не сохраняются.

### Team Readiness — компетенции команды

В разделе «Кабинет → Мои публикации» автор видит блок «Компетенции команды».

Endpoint:

```text
GET /publications/{id}/team-readiness
```

Доступен только автору соответствующей публикации.

Система показывает:

- количество принятых участников;
- покрытые распознанные компетенции;
- недостающие распознанные компетенции;
- подсказку, каких специалистов искать дальше.

Алгоритм учитывает навыки только тех кандидатов, чьи отклики приняты.

Не учитываются:

- отклики на рассмотрении;
- отклонённые отклики;
- навыки автора публикации;
- отклики на другие публикации.

Пример:

Требования:

```text
Python, UX/UI
```

Навыки принятого участника:

```text
пайтон
```

Результат:

- Покрыто: Python.
- Не покрыто: UX/UI.

Если принятых участников нет, отображается соответствующее пустое состояние.

Если требования не распознаны словарём, система прямо сообщает об ограничении анализа.

При частичном распознавании оценивается только известная словарю часть требований.

Полное покрытие распознанных навыков не означает, что команда полностью укомплектована.

## Принципы работы рекомендательного алгоритма

Рекомендации реализованы на основе явных правил и словаря компетенций.

**Это не машинное обучение и не LLM.**

Для работы не требуются платные AI API, API-ключи или внешние сервисы.

Преимущества подхода для MVP:

- объяснимость каждого совпадения;
- предсказуемое поведение;
- возможность тестирования;
- отсутствие дополнительных инфраструктурных расходов;
- переиспользование алгоритма в трёх механизмах подбора.

Ограничения:

- фиксированный словарь навыков;
- отсутствие понимания опечаток и сложных отрицаний;
- отсутствие проверки реального уровня опыта;
- отсутствие оценки доступности участников;
- неизвестные словарю компетенции не учитываются;
- повторный расчёт выполняется по текущим данным;
- исторические версии рекомендаций не сохраняются.

Подбор не заменяет общение между участниками и решение автора проекта.

Для масштабирования потребуются структурированные навыки, улучшенное индексирование и более гибкий поиск.

## Архитектурные решения

### FastAPI

FastAPI выбран благодаря удобной реализации REST API, встроенной OpenAPI-документации и поддержке dependency injection.

### PostgreSQL

Основные данные приложения сохраняются в PostgreSQL.

Структура базы изменяется через Alembic migrations.

### SQLAlchemy

SQLAlchemy используется как ORM между приложением и базой данных.

### JWT

Для защищённых endpoints используется JWT Bearer authentication.

JWT позволяет разграничивать доступ к операциям пользователей.

### React SPA

Frontend реализован как React Single Page Application.

Для маршрутизации используется React Router.

### nginx

При локальной Docker-сборке frontend собирается через Vite, после чего статические файлы раздаются nginx.

Для client-side routing настроен fallback на `index.html`.

### Docker Compose

Локальная инфраструктура содержит три сервиса:

```text
PostgreSQL
FastAPI
React/nginx
```

Это обеспечивает запуск проекта без отдельной ручной установки PostgreSQL или Node.js на компьютер проверяющего.

### Production

Backend опубликован на Railway.

PostgreSQL используется как production-база данных Railway.

Frontend опубликован на Cloudflare Workers.

Такой подход разделяет frontend и backend и позволяет проверяющему открыть работающую демонстрацию без локальной установки.

## Что намеренно не реализовано

В рамках тестового задания приоритет отдан работоспособности основного сценария, безопасности и удобству интерфейса.

Не реализованы:

- Telegram authentication;
- Telegram Mini App SDK;
- чат между участниками;
- WebSocket;
- push-уведомления;
- загрузка изображений;
- Redis;
- микросервисная архитектура.

Эти возможности не были необходимы для демонстрации основного пользовательского сценария и могли существенно увеличить сложность прототипа.

Архитектура позволяет в дальнейшем развивать приложение в сторону Telegram Mini App.

### Пример проверки решения, предложенного AI

ИИ предложил импортировать `User` в `app/db/base.py`, но при этом `user.py` уже импортировал `Base` из `base.py`.

Из-за этого возник циклический импорт, и приложение перестало запускаться.

Я посмотрел traceback, нашёл источник проблемы и убрал лишний импорт из `base.py`.

После этого модели стал импортировать отдельно там, где они действительно нужны, например для Alembic.

Затем снова запустил проект и убедился, что `uvicorn` стартует без ошибки.
