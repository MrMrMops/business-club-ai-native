# Business Club Startups

Рабочий прототип модуля стартапов и вакансий для приложения Бизнес-клуба.

Сервис позволяет участникам Бизнес-клуба находить команду для стартапа, публиковать вакансии в свои проекты и откликаться на интересные предложения.

## Возможности

Пользователи могут:

- создавать стартапы и вакансии;
- просматривать ленту предложений;
- фильтровать стартапы и вакансии;
- открывать подробную информацию о публикации;
- откликаться на предложения;
- принимать и отклонять входящие отклики;
- отслеживать статус своих откликов;
- редактировать профиль;
- управлять собственными публикациями;
- закрывать и повторно открывать публикации.
- полностью удалять собственные публикации вместе со связанными откликами.
- видеть имя автора из базы данных в ленте и на странице публикации.

## Основной сценарий

Основной пользовательский сценарий реализован следующим образом:

1. Пользователь входит в приложение.
2. Создаёт стартап или вакансию.
3. Другой пользователь находит публикацию в общей ленте.
4. Открывает подробности публикации.
5. Отправляет отклик с сообщением.
6. Автор публикации видит отклик в личном кабинете.
7. Автор принимает или отклоняет отклик.
8. Откликнувшийся пользователь видит итоговый статус в своём личном кабинете.

Один пользователь может одновременно быть автором собственных публикаций и откликаться на публикации других участников.

## Личный кабинет

В личном кабинете доступны четыре раздела.

### Профиль

Пользователь может:

- просматривать имя и email;
- изменять имя;
- добавлять информацию о себе;
- указывать навыки.

### Мои публикации

Пользователь может:

- просматривать свои стартапы и вакансии;
- открывать публикацию;
- редактировать название;
- редактировать описание;
- изменять информацию о том, кого он ищет;
- закрывать публикацию;
- повторно открывать закрытую публикацию.
- удалить публикацию после подтверждения; связанные с ней отклики при этом также удаляются.

### Мои отклики

Показываются все отправленные пользователем отклики и их текущий статус.

Возможные статусы:

- На рассмотрении;
- Принят;
- Отклонён.

### Входящие отклики

Автор публикации может:

- видеть входящие отклики;
- читать сообщение кандидата;
- принять отклик;
- отклонить отклик.

## Публикации

Есть два типа публикаций:

```text
startup
vacancy
```

### Жизненный цикл публикации

```text
active -> closed -> active
```

Активные публикации отображаются в общей ленте.

Закрытые публикации:

- не отображаются в общей ленте;
- остаются доступны автору в личном кабинете;
- не принимают новые отклики;
- могут быть повторно открыты.

---

## Отклики

### Жизненный цикл отклика

```text
pending -> accepted
        -> rejected
```

После принятия или отклонения отклика повторное изменение решения запрещено.

## Ограничения доступа и безопасность

В приложении реализовано разграничение доступа.

### Публикации

- создать публикацию может только авторизованный пользователь;
- редактировать публикацию может только её автор;
- изменить статус публикации может только её автор.
- удалить публикацию может только её автор; связанные отклики удаляются в рамках той же операции.

### Отклики

- откликнуться может только авторизованный пользователь;
- пользователь не может откликнуться на собственную публикацию;
- пользователь не может дважды откликнуться на одну публикацию;
- нельзя откликнуться на закрытую публикацию;
- обрабатывать отклик может только автор соответствующей публикации;
- нельзя повторно принять или отклонить уже обработанный отклик.

### Authentication

Для защищённых API endpoints используется JWT Bearer authentication.

Пароли пользователей не сохраняются в открытом виде.

В базе хранится только хеш пароля.

## API

### Authentication

```text
POST /auth/register
POST /auth/login
```

### Users

```text
GET   /users/me
PATCH /users/me
GET   /users/me/publications
```

### Publications

```text
GET   /publications
GET   /publications/{id}
POST  /publications
PATCH /publications/{id}
DELETE /publications/{id}
```

Ответы API публикаций содержат `author_id` и `author_name`.
Имя загружается вместе с публикацией из таблицы пользователей и отражает
изменения профиля. Email, хеш пароля, биография и навыки автора в эти ответы
не включаются. Изменение не требует миграции базы.

`DELETE /publications/{id}` доступен только автору для активных и закрытых
публикаций. Успешный ответ — `204` без тела; без авторизации — `401`,
для чужой публикации — `403`, для отсутствующей — `404`.
Удаление откликов и публикации выполняется одной транзакцией.
Пользователи, другие публикации и их отклики сохраняются.
В кабинете удаление требует подтверждения; отмена не отправляет запрос.

### Applications

```text
POST  /publications/{id}/applications

GET   /applications/sent
GET   /applications/received

PATCH /applications/{id}/accept
PATCH /applications/{id}/reject
```

Интерактивная документация API доступна после запуска приложения:

```text
http://localhost:8000/docs
```

## Двусторонний подбор команды

- **Smart Matching:** студент → подходящие проекты.
- **Reverse Matching:** автор проекта → соответствие навыков откликнувшихся кандидатов требованиям.

### Smart Matching — персональные рекомендации

Авторизованный `GET /publications/recommended` возвращает до трёх активных
публикаций других пользователей. Навыки из `User.skills` сопоставляются с
требованиями `Publication.looking_for` по небольшому явному словарю синонимов.
Регистр и пунктуация нормализуются; сравниваются целые слова и последовательности
слов, поэтому `Java` не совпадает с `JavaScript`, а `SQL` — с `NoSQL`.
Примеры: `backend` ↔ `бэкенд`, `UX/UI` ↔ `дизайн интерфейсов`,
`Python` ↔ `пайтон`, `product analytics` ↔ `продуктовая аналитика`.

Порядок: больше различных совпавших навыков — выше; при равенстве сначала
новые публикации (дата создания, затем ID). Повторы одного навыка не повышают
позицию. Ответ содержит обычные публичные поля публикации, `matched_skills`
и `explanation`; приватные поля автора не добавляются. Процент соответствия
не вычисляется. При пустых навыках или отсутствии совпадений возвращается `[]`.

Над лентой показаны карточки с совпавшими навыками и объяснением «Почему вам
подходит». Для пустого профиля есть переход к заполнению навыков, для отсутствия
совпадений — подсказка. Ошибка рекомендаций не блокирует обычную ленту.

Это объяснимый алгоритм по правилам, **не машинное обучение и не LLM**;
внешние AI API, ключи и платные сервисы не нужны. Словарь ограничен:
неизвестные навыки, опечатки и неуказанные формы слов не распознаются.
Алгоритм не понимает отрицания, уровень опыта и обязательность требований.
Описание не участвует в подборе, чтобы упоминание уже имеющихся технологий
не воспринималось как требование. Уже отправленные отклики не исключаются.
Для MVP рассматриваются все активные чужие публикации; для большого каталога
понадобятся индексирование навыков и более экономный поиск кандидатов.

### Reverse Matching — подсказки автору проекта

В «Кабинет → Входящие» отображаются имя кандидата, блок «Соответствие навыков»,
бейджи и объяснение «Почему кандидат подходит». Авторизованный
`GET /applications/received` добавляет `applicant_name`, `matched_skills` и
`explanation` только к откликам на публикации текущего пользователя.
Нового публичного списка кандидатов нет; email, биография, полный список навыков,
пароли и хеши не добавляются в ответ. Отправленные отклики сохраняют прежний формат.

Оба направления используют общие функции и словарь `app/services/matching.py`.
Например, навыки кандидата `Python, FastAPI, Backend` и требования
`Python, бэкенд` дают `Backend, Python`. При пустом профиле показано
«Кандидат пока не указал навыки», при отсутствии совпадений — нейтральная подсказка:
это не означает, что кандидат не подходит. Проценты и рейтинги не вычисляются.
Кнопки «Принять» и «Отклонить» работают как прежде: решение остаётся за автором.

Результат пересчитывается при запросе по текущему профилю и требованиям, включая
отклики на закрытые публикации и уже обработанные отклики; исторический снимок
не сохраняется. Подбор не проверяет реальное владение навыком и имеет те же
ограничения словаря, что Smart Matching. Это не искусственный интеллект,
не ML и не LLM; внешние API и изменения схемы базы не требуются.

### Team Readiness — компетенции формируемой команды

В «Кабинет → Мои публикации» блок «Компетенции команды» показывает покрытые
и недостающие распознанные навыки, число принятых участников и подсказку,
кого искать дальше. `GET /publications/{id}/team-readiness` доступен только
автору публикации (401 без авторизации, 403 для другого пользователя).
В ответе только агрегированные компетенции, без имён и личных данных кандидатов.

Навыки **только принятых** кандидатов объединяются и сравниваются с полем
«Ищем» теми же функциями `extract_skills` и `matched_skills`, что используются
в Smart Matching и Reverse Matching. Ожидающие и отклонённые отклики, навыки
автора и отклики на другие публикации не учитываются. Например, требования
`Python, UX/UI` и принятый участник с `пайтон` дают покрытый `Python` и
недостающий `UX/UI`. Без принятых откликов показывается пустое состояние.

Если требования не распознаны, анализ прямо сообщает об этом. При частичном
распознавании оценивается только известная словарю часть; предупреждение об
ограничениях показано всегда. Покрытие всех распознанных навыков не означает
полную укомплектованность: уровень опыта, отрицания, доступность участников
и неизвестные словарю компетенции не оцениваются. Нет процентов, ML, LLM
или внешних API. Данные пересчитываются по текущим профилям и требованиям,
в том числе для закрытых публикаций; исторические снимки не сохраняются.
Блок обновляется при открытии вкладки «Мои публикации» и изменении требований.
Для MVP выполняется один запрос на публикацию; для большого списка потребуется
пакетная загрузка. Схема базы и существующий механизм принятия не изменены.

## Тесты

Автоматические тесты написаны с использованием pytest.

Для тестов используется отдельная SQLite database in memory, поэтому тестовый запуск не затрагивает основную PostgreSQL базу.

Тесты покрывают:

- регистрацию пользователя;
- вход пользователя;
- повторную регистрацию с одинаковым email;
- вход с неверным паролем;
- создание публикации;
- запрет редактирования чужой публикации;
- запрет удаления чужой публикации;
- запрет удаления публикации без авторизации;
- удаление публикации автором вместе со связанными откликами;
- скрытие закрытой публикации из общей ленты;
- полный сценарий создания и обработки отклика;
- повторный отклик;
- отклик на собственную публикацию;
- попытку обработки отклика посторонним пользователем;
- повторную обработку уже принятого или отклонённого отклика.

отсутствие приватных полей, ручное принятие/отклонение и закрытые публикации.

объединение навыков и синонимов, изоляцию публикаций, исключение автора,
пустые профили, неизвестные и частично распознанные требования, закрытые
публикации, обновление навыков и требований, права доступа и минимальный ответ.

Тесты также проверяют актуальное имя автора и точный набор публичных полей
ответа API; удаление активных и закрытых публикаций с ожидающими, принятыми
и отклонёнными откликами; сохранение пользователей и несвязанных записей.

Frontend:

```bash
cd frontend
npm ci
npm run lint
npm run build
```

`npm run lint` и `npm run build` прошли после установки зависимостей через
`npm ci`. В Chrome на локальной сборке с тестовыми ответами API проверены
имена авторов в ленте и подробностях, отмена и подтверждение удаления
активной и закрытой публикации, обработка пустого ответа `204`.
Ошибок JavaScript в этих сценариях не обнаружено.

Проверки выполняются локально. Рабочая Railway/PostgreSQL не используется
в автоматических тестах.

## Архитектурные решения

### FastAPI

FastAPI выбран из-за простой реализации REST API, встроенной OpenAPI-документации и удобной системы dependency injection.

### PostgreSQL

Основные данные приложения сохраняются в PostgreSQL.

Структура базы изменяется через Alembic migrations.

### SQLAlchemy

SQLAlchemy используется как ORM между приложением и базой данных.

### JWT

Для прототипа используется JWT Bearer authentication.

Это позволяет тестировать приложение под разными пользователями и разграничивать доступ к защищённым действиям.

### React SPA

Frontend реализован как React Single Page Application.

Для маршрутизации используется React Router.

### nginx

Для финального Docker-запуска frontend сначала собирается через Vite, после чего статические файлы раздаются nginx.

Для поддержки client-side routing настроен fallback на index.html.

### Docker Compose

Docker Compose поднимает три сервиса:

```text
PostgreSQL
FastAPI
React/nginx
```

Это позволяет запустить весь проект одной командой без ручной установки PostgreSQL, Python или Node.js.

## Что намеренно не реализовано

В рамках тестового задания я решил не добавлять функциональность, которая не требуется для демонстрации основного сценария и значительно увеличивает сложность прототипа.

Не реализованы:

- Telegram authentication;
- Telegram Mini App SDK;
- чат между участниками;
- WebSocket;
- push-уведомления;
- загрузка изображений;
- Redis;
- микросервисная архитектура.

Основной приоритет был отдан работоспособности основного пользовательского сценария, понятной модели данных, разграничению доступа и удобному интерфейсу.

Архитектура frontend позволяет позднее встроить интерфейс в Telegram Mini App.

AI использовался для:

- обсуждения структуры проекта;
- подготовки первоначальных вариантов модели данных;
- помощи при проектировании REST API;
- генерации отдельных фрагментов backend;
- генерации отдельных компонентов frontend;
- поиска причин возникающих ошибок;
- подготовки вариантов автоматических тестов;
- обсуждения Docker-конфигурации.

Предложенные AI решения не принимались автоматически.

Они проверялись:

- ручным запуском приложения;
- запросами через Swagger;
- проверкой основного сценария под несколькими пользователями;
- автоматическими pytest-тестами.

### Проверка решения, предложенного AI

ИИ предложил импортировать `User` в `app/db/base.py`, но при этом `user.py` уже импортировал `Base` из `base.py`. Из-за этого возник циклический импорт, и приложение перестало запускаться. Я посмотрел traceback, нашёл источник проблемы и убрал лишний импорт из `base.py`. После этого модели стал импортировать отдельно там, где они действительно нужны, например для Alembic. Затем снова запустил проект и убедился, что `uvicorn` стартует без ошибки.

## Запуск с нуля

Краткая инструкция для проверяющего:

```bash
git clone https://github.com/MrMrMops/business-club-ai-native.git
cd business-club-ai-native

docker compose up --build
```

После запуска:

```text
Frontend:
http://localhost:5173

Swagger:
http://localhost:8000/docs
```

Создать демонстрационные данные:

```bash
docker compose exec backend python -m app.db.seed
```

Войти, например:

```text
Email:
nikita@example.com

Password:
password123
```
